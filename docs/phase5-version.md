# Phase 5: version カラムを利用した楽観的ロック

## 考え方

仕組みは Phase 4 の updated_at 方式とほぼ同じです。

- 編集中はロックを取りません。
- 保存の瞬間に「編集画面を開いたときから、行が変わっていないか」を UPDATE の WHERE 句で確認します。

違いは目印です。時刻の代わりに、**更新のたびに必ず 1 増える排他制御専用の番号**（version）を使います。

---

## なぜこの実装が必要なのか

Phase 4 で、updated_at 方式には次の弱点があることを確認しました。

- 秒単位でしか記録されないので、同じ秒の中で起きた更新を見逃す。
- 業務上の「最終更新日時」と兼用しているので、`touch()` など内容と関係ない処理でも値が変わる。

version は「何回更新されたか」を数える番号なので、同じ秒に何回更新されても必ず値が変わります。
また排他制御のためだけのカラムなので、業務の都合で値が動くことがありません。

---

## 排他制御のタイミング

| タイミング | 何が起きるか |
|---|---|
| 編集画面を開く | 何もしない。hidden に version を埋め込むだけ |
| 編集中 | 何もしない。他の人も自由に編集画面を開ける |
| **保存（UPDATE）** | WHERE 句に `version = 開いた時点の値` を加え、同時に `version = version + 1` にする |

```html
<input type="hidden" name="original_version" value="1">
```

---

## 発行される SQL

A と B が version = 1 の時点で編集画面を開き、A → B の順に保存したときの実際のログです。

```sql
-- A の保存: version = 1 の行が見つかるので 1 件更新。version は 2 になる
update `reservations`
   set `customer_name` = '山田 太郎', `number_of_people` = '4',
       `reservation_date` = '2026-10-10 19:00:00', `status` = 'pending',
       `version` = version + 1, `reservations`.`updated_at` = '2026-10-03 18:07:54'
 where `reservations`.`id` = 1 and `version` = 1

-- B の保存: version はもう 2 なので一致する行が無く、0 件更新
update `reservations`
   set ..., `number_of_people` = '2', `status` = 'confirmed',
       `version` = version + 1, ...
 where `reservations`.`id` = 1 and `version` = 1
```

Phase 4 の SQL との違いは、WHERE 句の条件と、SET 句の `version = version + 1` だけです。

---

## 競合した場合に何が起こるか

Phase 4 と同じです。

1. 0 件更新なので `ReservationConflictException` を投げます。
2. 入力内容を残したまま編集画面に戻し、「最新の内容」と「あなたの入力」を並べて表示します。
3. 編集画面は DB から最新の version（2）を hidden に入れ直すので、内容を確認して保存し直すと成功します。

```
version の推移:  1 →(A)→ 2 →(B 競合)→ 2 →(B 再保存)→ 3
```

## updated_at 方式との比較実験

### 実験 1: 同じ秒の中で更新された場合

Phase 4 で updated_at 方式が見逃した手順を、2 つの方式でまったく同じように実行しました。

```
手順（すべて 1 秒以内に行う）
  1. A が人数を 4 に保存
  2. B が編集画面を開く
  3. A がもう一度開いて人数を 6 に保存
その後
  4. B がステータスだけ確定にして保存（人数はフォームに残っている 4 のまま）
```

| | B が開いた時点の hidden | A の 2 回目の保存後の DB | B の保存 | 最終的な人数 |
|---|---|---|---|---|
| updated_at | updated_at = 18:08:09 | updated_at = 18:08:09（変わらない） | **成功してしまう** | 4（A の 6 が消えた） |
| version | version = 2 | version = 3 | **競合で止まる** | 6（守られた） |

B の UPDATE の WHERE 句はそれぞれ次のとおりです。

```sql
-- updated_at 方式: A の 2 回目の更新後も 18:08:09 のままなので一致してしまう
where `reservations`.`id` = 1 and `updated_at` = '2026-10-03 18:08:09'

-- version 方式: A の 2 回目の更新で 3 になっているので一致しない
where `reservations`.`id` = 1 and `version` = 2
```

### 実験 2: 同じ version を持つ保存を 10 件同時に送る

10 人が同じ時点で編集画面を開き、10 件の保存リクエストを同時に送りました。

| 方式 | 成功 | 競合 | 最終的な DB |
|---|---|---|---|
| 排他制御なし | 10 件 | 0 件 | 最後に処理された 1 件の内容。他の 9 件の変更は消えた |
| version | **1 件** | **9 件** | 最初に処理された 1 件の内容。version = 2 |

10 件の UPDATE 文はほぼ同じ時刻（同じミリ秒のものもある）に MySQL に届いています。それでも成功は 1 件だけでした。

```
18:08:28.515  1544  update ... `version` = version + 1 ... where `reservations`.`id` = 1 and `version` = 1
18:08:28.515  1545  update ... `version` = version + 1 ... where `reservations`.`id` = 1 and `version` = 1
18:08:28.534  1547  update ... `version` = version + 1 ... where `reservations`.`id` = 1 and `version` = 1
...
```

**なぜ 1 件だけになるのか:**

1. InnoDB は UPDATE の対象行に排他ロック（行ロック）を取ってから WHERE 句を評価します。
2. 最初にロックを取った UPDATE が version を 2 にしてコミットするまで、他の 9 件はロック待ちになります。
3. ロックが外れると、待っていた UPDATE は **最新のコミット済みの行** を読んで WHERE 句を評価し直します。version はもう 2 なので一致せず、0 件更新になります。

楽観的ロックは「アプリではロックを取らない」方式ですが、UPDATE 文の内部では DB の行ロックが働いています。
確認と更新を 1 つの UPDATE 文にまとめることで、この行ロックを利用して同時実行でも正しく判定できます。

## 実装のポイント

### version を増やすのは SQL の式で書く

```php
'version' => DB::raw('version + 1'),
```

WHERE 句で `version = 1` を確認しているので、PHP で計算した `2` を SET しても結果は同じです。
SQL の式にしておくと、SQL を読むだけで「今の値に 1 を足す」という意図が分かります。
また、WHERE 条件を書き忘れるミスをした場合でも、番号が巻き戻ることがありません。

### version はフォームから一括代入させない

Phase 2 でモデルの `$fillable` から version を外しています。
もしフォームから version を書き換えられると、悪意のあるリクエストで version を巻き戻し、他の人の保存を競合にできてしまいます。
version を書き換えるのは、`VersionLockUpdater` の `version + 1` だけです。

### hidden の version が改ざんされた場合

| 送られてきた値 | 結果 |
|---|---|
| `abc` など数値でない値 | 形式エラー。「編集開始時のバージョンが不正です」と表示し、更新しない |
| `999` など DB と一致しない数値 | WHERE 句に一致しないので競合として扱い、更新しない |

どちらの場合も DB は変わりません。
最新の version を送れば保存できますが、それは「最新の内容を見たうえで保存した」のと同じ扱いになるので問題ありません。

---

## 弱点

### 弱点 1: すべての更新処理で version を増やす必要がある

version 方式が正しく動くのは、**行を更新するすべての処理が version を +1 する** 場合だけです。

- 管理画面、API、バッチ、手作業の SQL などで version を増やさずに更新すると、その更新は検知できません。
- このアプリでも、「排他制御なし」と「updated_at」の方式で保存した場合は version が増えません。

updated_at は Eloquent が自動で更新してくれますが、version は自分で増やす必要があります。
実務では、モデルイベントや共通の更新処理で必ず増やすようにして、増やし忘れを防ぎます。

### 弱点 2: 競合に気づくのが保存の瞬間

これは楽観的ロック全般の弱点です。

B は長い時間をかけて入力しても、保存ボタンを押した瞬間に初めて「他の人が先に更新した」と知ります。
入力内容は画面に残りますが、最新の内容と見比べて入力し直す手間がかかります。

競合が頻繁に起きる業務や、入力に時間がかかる画面では、「そもそも同時に編集させない」ほうが親切な場合があります。
これが Phase 7 の編集ロックの考え方です。

## 他の方式との違い

| | 排他制御なし | updated_at | version |
|---|---|---|---|
| 編集画面を開くとき | 何もしない | updated_at を hidden に入れる | version を hidden に入れる |
| 保存時の WHERE 句 | `id = ?` | `id = ? and updated_at = ?` | `id = ? and version = ?` |
| 保存時の SET 句 | 変わったカラム | 全カラム（updated_at は自動） | 全カラム + `version = version + 1` |
| 同じ秒の更新 | - | **見逃す** | 検知する |
| 追加のカラム | 不要 | 不要 | 必要（version） |
| 増やし忘れのリスク | - | 少ない（Eloquent が自動更新） | ある（自分で +1 する） |
| 競合に気づくタイミング | 気づけない | 保存時 | 保存時 |

新しく作るシステムで楽観的ロックを使うなら、version 方式が一般的です。
JPA（Java）の `@Version` や Rails の `lock_version` など、多くのフレームワークが標準でこの方式を採用しています。
