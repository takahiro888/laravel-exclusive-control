# Phase 3: 排他制御なしで Lost Update を再現する

## Lost Update とは

2人が同じデータを読み込み、それぞれ編集して保存したときに、**先に保存した人の変更が、後から保存した人の内容で消えてしまう** 現象です。
どちらの保存もエラーにならず「更新しました」と表示されるため、誰も気づけないのが問題です。

---

## 再現手順

利用者 A と B を、2つのタブ（または2つのブラウザ）で再現します。
Phase 3 時点ではセッションに依存する処理が無いので、同じブラウザの2タブでも再現できます。

### 準備

```sh
# データを初期状態に戻す（予約 ID=1 が「山田 太郎 / 2名 / 仮予約」になる）
docker compose exec app php artisan migrate:fresh --seed

# 別のターミナルで、発行される SQL を監視しておく
docker compose exec db tail -f /var/lib/mysql/general.log
```

画面上部の「排他制御方式」が **排他制御なし** になっていることを確認します。

### 手順

| # | 利用者 A（タブ1） | 利用者 B（タブ2） |
|---|---|---|
| 1 | 予約 #1 の編集画面を開く（2名 / 仮予約） | |
| 2 | | 予約 #1 の編集画面を開く（2名 / 仮予約） |
| 3 | 人数を **4名** に変えて保存 →「更新しました」 | |
| 4 | | ステータスを **確定** に変えて保存 →「更新しました」 |
| 5 | 詳細画面を見ると **2名 / 確定** になっている | |

A が保存した「4名」が消えています。これが Lost Update です。

---

## 実際に発行された SQL

上の手順を実行したときの general log です（時刻以外は実際の出力そのまま）。

```
時刻      接続ID  SQL
16:52:32  460  select * from `reservations` where `id` = '1' limit 1      ← A が編集画面を開く
16:52:33  461  select * from `reservations` where `id` = '1' limit 1      ← B が編集画面を開く
16:52:34  462  select * from `reservations` where `id` = '1' limit 1      ← A の保存リクエスト
16:52:34  462  update `reservations` set `number_of_people` = '4', `reservations`.`updated_at` = '2026-10-03 16:52:34' where `id` = 1
16:52:36  465  select * from `reservations` where `id` = '1' limit 1      ← B の保存リクエスト
16:52:36  465  update `reservations` set `number_of_people` = '2', `status` = 'confirmed', `reservations`.`updated_at` = '2026-10-03 16:52:36' where `id` = 1
```

DB の値の推移:

| 時点 | number_of_people | status | version | updated_at |
|---|---|---|---|---|
| 初期状態 | 2 | pending | 1 | 16:52:32 |
| A 保存後 | 4 | pending | 1 | 16:52:34 |
| B 保存後 | **2** | confirmed | 1 | 16:52:36 |

## なぜ起きるのか

### 1. UPDATE の WHERE 句が id だけ

```sql
update reservations set ... where id = 1
```

「B が編集画面を開いた後に、誰かが更新したかどうか」を一切確認していません。
そのため B の UPDATE は、A の更新があった後でも必ず成功します。

### 2. フォームは「編集画面を開いた時点の値」をすべて送ってくる

B が変更したのはステータスだけです。しかし B のフォームには、開いた時点の「2名」が入ったままです。

### 3. Eloquent は「変わったカラムだけ」を UPDATE するが、それでも防げない

Eloquent の `save()` は、読み込んだ時点の値と比べて変わったカラムだけを UPDATE に含めます。
A の UPDATE に `status` が含まれていないのはこのためです。

一見すると「B もステータスだけを更新するから大丈夫」と思えます。しかし B の保存リクエストの中では、次のことが起きています。

1. 保存リクエストの先頭で、最新の行（**4名**）を読み込む
2. フォームの値（**2名**）を入れる
3. 4 → 2 に「変わった」と判断され、`number_of_people = '2'` が UPDATE に含まれる

Eloquent が比べているのは「保存リクエストの中で読み込んだ値」と「フォームの値」です。
「B が編集画面を開いた時点の値」とは比べていないので、A の変更を B の変更と区別できません。

### 4. 接続 ID から分かること

PHP-FPM はリクエストごとに新しい DB 接続を作るので、接続 ID が同じ行は1つのリクエストから出た SQL です。

- 編集画面を開くリクエスト（460, 461）と、保存のリクエスト（462, 465）は別の接続です。
- つまり「編集画面を開いてから保存するまで」の間、DB はその利用者のことを何も覚えていません。

これが Web アプリの排他制御の難しさです。
DB のトランザクションやロックは、1つの接続（1リクエスト）の中でしか効きません。
「画面を開いてから保存するまで」という複数リクエストにまたがる操作を守るには、アプリ側で工夫が必要になります。

---

## 次の Phase 以降でどう防ぐか

| 方式 | 防ぎ方 | B の保存はどうなるか |
|---|---|---|
| updated_at（Phase 4） | 編集開始時の updated_at を hidden で送り、`where id = 1 and updated_at = ?` で UPDATE する | 0件更新になり、競合エラー |
| version（Phase 5） | 編集開始時の version を hidden で送り、`where id = 1 and version = ?` で UPDATE し、version を +1 する | 0件更新になり、競合エラー |
| SELECT FOR UPDATE（Phase 6） | 保存トランザクションの中で行ロックを取る | 同時に保存した場合は待たされる。ただし単独では、画面を開いてからの変更は検知できない |
| 編集ロック（Phase 7） | 編集画面を開いた時点で locked_by を書き込む | B は編集画面を開いた時点で「A が編集中」と表示され、入れない |

SELECT FOR UPDATE の行に「単独では検知できない」と書いたのは、上の 4. の理由によるものです。
ロックは保存リクエストの中でしか効かないので、編集画面を開いてから保存するまでの変更は守れません。Phase 6 で実際に確かめます。

## 実装のポイント

### 方式ごとに更新クラスを分けている

```
app/Services/ReservationUpdaters/
├── ReservationUpdater.php          # 共通インターフェース
├── NoLockUpdater.php               # Phase 3: 排他制御なし
└── ReservationUpdaterFactory.php   # 方式 → クラスの対応表
```

コントローラは「現在の方式に対応するクラスに更新を任せる」だけです。
Phase 4 以降は Updater クラスを1つずつ追加していくので、`NoLockUpdater` と並べて読めば方式の違いがそのまま分かります。

### 方式はアプリ全体で1つ

方式の設定はセッションではなくキャッシュ（実体は MySQL の cache テーブル）に保存しています。
排他制御は「全員が同じルールに従う」ことで初めて意味があるため、A と B で方式がずれないようにしています。

### 編集中に方式が切り替わったら更新を止める

編集画面は、開いた時点の方式を hidden で送ります。保存時に現在の方式と違っていたら、更新せずに編集画面に戻します。
例えば「なし」で開いたフォームには version が含まれないので、そのまま version 方式で判定すると正しく動かないためです。
