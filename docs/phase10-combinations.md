# Phase 10: 異なる処理の組み合わせ（画面の操作 × バッチ）

## 検証したいこと

Phase 3〜7 は、「同じ画面を 2 人が同時に操作する」場合の検証でした。
実際のシステムでは、同じ予約を **別の処理** も変更します。

- 画面のキャンセル処理（楽観的ロック）
- 画面の編集
- 仮予約の一括確定バッチ
- 期限切れ仮予約の自動キャンセルバッチ

キャンセル処理どうしが同時に来ても、楽観的ロックで正しく処理できます。
問題は、**楽観的ロックのキャンセル処理と、排他制御をしていないバッチが同時に来た場合** です。
楽観的ロックで守っていても、バッチが後から古い前提のまま変更してしまえば意味がありません。

この Phase では、バッチの書き方を 5 通り用意し、5 つの場面で結果を比べて、どの組み合わせが最善かを決めます。

---

## 結論

**すべての書き込み経路（画面・API・バッチ）が、次の 2 つを守ること。**

1. **書き込むときに「読んだ時点の前提」を UPDATE の WHERE 句で確認する**（後出しを防ぐ）
2. **業務データを変えたら必ず version を上げる**（他の処理の楽観的ロックが変更に気づけるようにする）

予約ステータスを変えるバッチの最善の書き方は、**状態ガード + version** です。

```sql
update reservations
   set status = 'confirmed', version = version + 1, updated_at = ?
 where id = ?
   and status = 'pending'          -- 状態ガード: まだ仮予約のときだけ確定する
```

| 守ること | 片方だけだと何が起きるか（検証結果） |
|---|---|
| 1. WHERE 句で前提を確認 | これが無いと、利用者がキャンセルした予約をバッチが確定で上書きする（場面 1） |
| 2. version を上げる | これが無いと、バッチの確定を利用者の古いフォームが仮予約に戻す（場面 2） |

さらに、**キャンセルのように後から覆されては困る変更** は、DB のトリガーで状態遷移のルールそのものを強制して「最後の砦」にします。
どの処理が、どんな書き方で書き込んでも、「キャンセル済み → 確定」のような変更は DB が拒否します（後述）。

| 案 | 排他制御なしのバッチの後出しを防げるか | 利用者への影響 |
|---|---|---|
| キャンセル処理を悲観的ロックにする | **防げない**（検証済み） | ロック中は他の処理が待たされる |
| バッチ側に条件（状態ガード）を入れる | 防げる | なし |
| **キャンセルは楽観的ロックのまま + 状態遷移トリガー** | **防げる**（条件を入れ忘れたバッチや生の SQL からも） | なし（負荷の差は測定のばらつきの範囲内） |

**推奨: バッチ側に状態ガードを入れる + 状態遷移トリガーを最後の砦にする。キャンセル処理は楽観的ロックのままでよい。**
詳しくは「[後出しを防ぐのはどこか（3 つの案の比較）](#後出しを防ぐのはどこか3-つの案の比較)」を参照してください。

## 登場する処理

### 画面のキャンセル処理（楽観的ロック）

予約詳細画面の「この予約をキャンセルする」ボタンです。
画面上部の「排他制御方式」とは関係なく、常に version による楽観的ロックで処理します。

```sql
update reservations
   set status = 'cancelled', version = version + 1, updated_at = ?
 where id = 1
   and version = 1                            -- 画面を開いた時点の version
   and status in ('pending', 'confirmed')     -- キャンセルできる状態か（状態遷移のルール）
```

### ステータス一括変更バッチ

```sh
docker compose exec app php artisan reservations:change-status {変更前} {変更後} --strategy={書き方} [--id=予約ID] [--pause=秒]
```

どのバッチも「① 対象を読み込む → ② 1 件ずつ書き込む」の 2 段階です。
①と②の間に他の処理が同じ予約を変更すると、②は古い前提のまま書き込むことになります。
`--pause` を付けると①と②の間で待つので、その間に画面で操作して「後出し」を再現できます。

| 書き方（--strategy） | ② の SQL |
|---|---|
| なし（`none`） | `update ... set status = ? where id = ?` |
| 状態ガード（`state_guard`） | `update ... set status = ? where id = ? and status = 'pending'` |
| **状態ガード + version（`state_guard_version`）** | `update ... set status = ?, version = version + 1 where id = ? and status = 'pending'` |
| 楽観的ロック（`optimistic`） | `update ... set status = ?, version = version + 1 where id = ? and version = 読んだ時点` |
| 悲観的ロック（`pessimistic`） | 1 件ずつ `begin` → `select ... for update` → PHP で状態を確認 → `update` → `commit` |

### 状態遷移のルール

```
仮予約 ──→ 確定
  │         │
  └──→ キャンセル ←┘      キャンセルは終端（どこにも戻れない）
```

`ReservationStatus::canTransitionTo()` に定義し、キャンセル処理の WHERE 句とバッチの実行前チェックで使っています。
「キャンセル済み → 確定」のバッチは、実行しようとしても拒否されます。

## 検証した場面

| 場面 | 処理の順番 | 正しい結果 |
|---|---|---|
| 1. バッチの後出し | 確定バッチが読み込む → **利用者がキャンセル** → バッチが書き込む | キャンセルのまま |
| 2. 利用者の後出し | 利用者が編集画面を開く → **確定バッチ** → 利用者が人数だけ変えて保存 | 利用者が競合に気づく。確定のまま |
| 3. 知らずにキャンセル | 利用者が詳細画面を開く → **確定バッチ** → 利用者がキャンセル | 利用者が「確定済み」に気づける |
| 4. バッチ同士 | 確定バッチが読み込む → **自動キャンセルバッチ** → 確定バッチが書き込む | キャンセルのまま |
| 5. 関係ない編集 | 確定バッチが読み込む → **利用者が顧客名だけ変更** → バッチが書き込む | 確定される（顧客名の変更も残る） |

場面 3 について: 確定済みの予約をキャンセルすること自体は、遷移ルール上は許されます。
しかしキャンセル料が発生するなど、確定済みかどうかで利用者の判断が変わる業務では、利用者は気づけるべきです。

## 結果

`tests/Feature/CombinationTest.php` で、書き方 × 場面のすべての組み合わせを自動テストしています（25 通り、すべて期待どおり）。

| バッチの書き方 | 場面 1 バッチの後出し | 場面 2 利用者の後出し | 場面 3 知らずにキャンセル | 場面 4 バッチ同士 | 場面 5 関係ない編集 |
|---|---|---|---|---|---|
| なし | ❌ 確定で上書き | ❌ 仮予約に戻る | ⚠️ 気づけない | ❌ 確定で上書き | ✅ 確定 |
| 状態ガード | ✅ キャンセルのまま | ❌ 仮予約に戻る | ⚠️ 気づけない | ✅ キャンセルのまま | ✅ 確定 |
| **状態ガード + version** | ✅ キャンセルのまま | ✅ 競合で気づく | ✅ 気づける | ✅ キャンセルのまま | ✅ 確定 |
| 楽観的ロック | ✅ キャンセルのまま | ✅ 競合で気づく | ✅ 気づける | ✅ キャンセルのまま | ⚠️ 不要なスキップ |
| 悲観的ロック | ✅ キャンセルのまま | ✅ 競合で気づく | ✅ 気づける | ✅ キャンセルのまま | ✅ 確定 |

### なぜこうなるのか

**「なし」が場面 1 と 4 で失敗する理由:**
② の WHERE 句が id だけなので、①の後にキャンセルされていても確定で上書きします。
利用者のキャンセルは楽観的ロックで正しく成功していますが、その **後から** バッチが書き込むので防げません。

**「状態ガード」が場面 2 と 3 で失敗する理由:**
後出しは防げますが、version を上げません。
編集画面を開いている利用者の楽観的ロック（`where version = 1`）は、バッチの変更に気づけずに成功します。
その結果、利用者のフォームに残っていた「仮予約」で、バッチの確定が戻ります。

> 補足: updated_at 方式の楽観的ロックの場合は、Eloquent がバッチの UPDATE でも updated_at を自動で更新するので、利用者は気づけます。
> ただし生の SQL のバッチや、同じ秒の更新（Phase 4 の弱点）では気づけません。

**「楽観的ロック」が場面 5 でスキップする理由:**
version は「何かが変わった」ことしか分かりません。顧客名が変わっただけでも version が変わるので、確定してよい予約までスキップします。
データが壊れるわけではなく、次回のバッチで確定されますが、処理が遅れます。

**「状態ガード + version」がすべて成功する理由:**

- 状態ガードは「ステータスがまだ仮予約か」だけを確認するので、関係ない変更ではスキップしない（場面 5）。
- それでいて、キャンセルされた予約はステータスが変わっているので確定しない（場面 1・4）。
- version を上げるので、画面を開いている利用者が変更に気づける（場面 2・3）。

**「悲観的ロック」もすべて成功するが、推奨しない理由:**
1 件ずつ短いトランザクションでロックを取っているので結果は正しくなります。
しかし件数分のトランザクションが必要で、ロック中は画面の操作が待たされます。
状態ガードの UPDATE 1 文でも、InnoDB の行ロックにより同じ安全性が得られます（Phase 5 の 10 件同時実験を参照）。
悲観的ロックが必要なのは、「関連する別のテーブルも読んで、整合性を確認してから書く」ような場合です。

## 実際の同時実行での確認

バッチを `--pause=4` で起動し、待っている間に画面からキャンセルしました。

### バッチの書き方: なし

```
02:09:04.825  22794  select * from `reservations` where `status` = 'pending' and `reservations`.`id` in (1) ...   ← バッチが読み込む
02:09:06.725  22796  update `reservations` set `status` = 'cancelled', `version` = version + 1, ...
                     where `reservations`.`id` = 1 and `version` = 1 and `status` in ('pending', 'confirmed')     ← 利用者のキャンセル（成功）
02:09:08.830  22794  update `reservations` set `status` = 'confirmed', ... where `id` = 1                        ← バッチの後出し
```

| 時点 | status | version |
|---|---|---|
| 初期 | pending | 1 |
| 利用者のキャンセル後（画面には「予約をキャンセルしました」） | cancelled | 2 |
| バッチの書き込み後 | **confirmed** | 2 |

利用者の画面には「キャンセルしました」と表示されたのに、2 秒後に確定に戻りました。
version も 2 のままなので、後からこの予約を開いた人も、バッチが変更したことに気づけません。

### バッチの書き方: 状態ガード + version

```
02:09:10.180  22804  select * from `reservations` where `status` = 'pending' and `reservations`.`id` in (1) ...   ← バッチが読み込む
02:09:12.088  22806  update `reservations` set `status` = 'cancelled', `version` = version + 1, ...                ← 利用者のキャンセル（成功）
02:09:14.190  22804  update `reservations` set `status` = 'confirmed', `version` = version + 1, ...
                     where `reservations`.`id` = 1 and `status` = 'pending'                                       ← 0 件（status がもう pending ではない）
```

バッチの出力:

```
| ID | 結果     | 理由                                          |
| 1  | スキップ | 読み込んだ後に、状態が「仮予約」から変わっていた |
```

キャンセルが守られ、バッチはこの予約をスキップしたことを記録しました。

## DB トリガーで version の上げ忘れを防ぐ

「すべての書き込み経路で version を上げる」は、ルールとして決めても、生の SQL や新しく作ったバッチで忘れられがちです。
そこで、DB のトリガーで強制する方法を検証しました（`tests/Feature/VersionTriggerTest.php`）。

```sql
CREATE TRIGGER reservations_bump_version BEFORE UPDATE ON reservations
FOR EACH ROW
BEGIN
    -- 業務データが変わる UPDATE なら、アプリが何を SET したかに関係なく version を上げる
    IF NOT (NEW.customer_name <=> OLD.customer_name
        AND NEW.number_of_people <=> OLD.number_of_people
        AND NEW.reservation_date <=> OLD.reservation_date
        AND NEW.status <=> OLD.status) THEN
        SET NEW.version = OLD.version + 1;
    END IF;
END
```

| 確認したこと | 結果 |
|---|---|
| version に触れない生の SQL でステータスを変える | version が上がる |
| アプリが `version = version + 1` を SET する | 二重には上がらない（トリガーが OLD + 1 で上書き） |
| 編集ロックの取得（locked_* だけの UPDATE） | version は上がらない |
| **効く:** 「なし」のバッチ × 場面 2 | 利用者が競合に気づけるようになった |
| **効かない:** 「なし」のバッチ × 場面 1 | キャンセルは確定で上書きされたまま |

トリガーは「変更があったことを他の処理に知らせる」ことはできますが、
「読んだ時点の前提が変わっていたら書かない」という判断はできません。
**後出しを防ぐには、書き込む側が WHERE 句で前提を確認するしかありません。**

トリガーの注意点:

- バイナリログが有効な MySQL では、SUPER 権限が無いとトリガーを作れない（このテストでもエラー 1419 になり、root で作成した）。
- 業務ロジックが DB に隠れるので、アプリのコードだけを読んでも挙動が分からない。
- 業務データのカラムを追加したら、トリガーの条件も更新する必要がある。

## 編集ロックとバッチの組み合わせ（弱点）

推奨の書き方（状態ガード + version）のバッチでも、利用者側が **version を確認しない編集ロック方式**（Phase 7）だと防げませんでした。

```
A が編集画面を開く（編集ロックを取得）
確定バッチが実行される → 確定（バッチは編集ロックを確認しない）
A が人数だけ変えて保存 → 成功（保存の条件は locked_by = 'A' だけ）
→ ステータスが A の古いフォームの「仮予約」に戻る
```

`CombinationTest` の「弱点 編集ロック中の予約をバッチが確定するとロック保持者の保存で戻ってしまう」で確認しています。

編集ロックは「画面どうし」の約束なので、その約束に参加しないバッチからは守れません。対策は次のどちらか、または両方です。

- 編集ロックの保存でも version を確認する（**編集ロック + version**）。
- バッチが、有効な編集ロックがかかっている予約をスキップする（`where locked_by is null or locked_until < NOW()`）。

この結果からも、「すべての経路が version を上げ、すべての経路が version（または状態）を確認する」ことが、方式の組み合わせに左右されない最も確実な土台だと分かります。

## 画面が updated_at 方式の場合

現場では version カラムが無く、updated_at で楽観的ロックをしていることが多いので、その場合も確認しました（`tests/Feature/UpdatedAtCombinationTest.php`）。

| 場面 | バッチの書き方 | 結果 |
|---|---|---|
| バッチの後出し（利用者が編集画面でキャンセル → バッチが書く） | なし | ❌ キャンセルが確定で上書きされる |
| 同上 | 状態ガード | ✅ キャンセルのまま |
| 利用者の後出し（利用者が開く → バッチ → 利用者が保存） | 状態ガード（Eloquent で書く。別の秒） | ✅ 競合で気づける |
| 同上 | 状態ガード（`DB::table()` で書く。updated_at を更新しない） | ❌ 確定が仮予約に戻る |
| 同上 | 状態ガード（Eloquent で書く。**利用者が開いたのと同じ秒**） | ❌ 確定が仮予約に戻る |

### 画面が updated_at で確認しているのに、バッチの後出しを防げない理由

```sql
-- ① 利用者のキャンセル: 開いた時点の updated_at で確認して成功する
update reservations set status = 'cancelled', updated_at = '10:00:01'
 where id = 1 and updated_at = '10:00:00'

-- ② バッチの後出し: 条件が id だけなので、updated_at が何であっても一致して成功する
update reservations set status = 'confirmed', updated_at = '10:00:02'
 where id = 1
```

- updated_at の確認は、① の UPDATE が実行される一瞬だけの判定です。① が終わった後、DB には「この行は守られている」という印は何も残りません。
- 「開いたときから変わっていないか」を確認しているのは、① の UPDATE だけです。② の UPDATE は確認していません。
- **楽観的ロックが防ぐのは「自分が後から書いて、他の人の変更を消すこと」だけ** です。他の処理が後から書くことは、その処理が確認しない限り防げません。

### updated_at 方式の現場で確認すること

- すべてのバッチの UPDATE に、読んだ時点の前提の条件があるか（`status = 変更前`、または `updated_at = 読んだ値`）。
- すべてのバッチが updated_at を更新しているか。Eloquent のモデルや Builder は自動で更新しますが、`DB::table()` や生の SQL は更新しないので、`updated_at = NOW()` を明示する必要があります。
- 画面とバッチの更新が同じ秒に重なりうるか。重なりうるなら version カラムの追加を検討します（Phase 4 の弱点）。

## 後出しを防ぐのはどこか（3 つの案の比較）

「キャンセルのように、後から覆されては困る処理をどう守るか」について、3 つの案を検証しました。

### 案 1: キャンセル処理を悲観的ロックにする → 防げない

`tests/Feature/PessimisticCancelTest.php` で、キャンセル処理を `SELECT ... FOR UPDATE` で行い、排他制御なしのバッチと組み合わせました。

| 状況 | 結果 |
|---|---|
| キャンセルがコミットした後に、バッチが書き込む | ❌ 確定で上書きされる |
| キャンセルがロックを持っている間に、バッチが書き込む | ❌ バッチは 2 秒待たされた後、確定で上書きする |

悲観的ロックが他の処理を止められるのは、**ロックを持っている間だけ** です。
キャンセルがコミットしてロックを外した後に来た UPDATE は、そのまま実行されます。
ロック中に来た UPDATE も、待たされるだけで、ロックが外れた後に実行されます。

後出しを防ぐ力は、**先に書く側のロック** ではなく、**後から書く側の条件** にあります。
キャンセル処理をどれだけ強く守っても、後から来るバッチが確認しなければ防げません。
しかも悲観的ロックにすると、ロック中は同じ予約への他の操作が待たされるので、利用者の多いサービスでは損しかありません。

### 案 2: バッチ側に条件を入れる → 防げる

この Phase の結果のとおり、状態ガード（`where status = 'pending'`）を入れたバッチは、キャンセル済みの予約を確定しません。
ロックを取らないので、利用者への影響もありません。

ただし、**すべてのバッチ・すべての書き込み経路が正しく書かれている** ことが前提です。
- 古いバッチ、別チームが作ったバッチ、緊急対応の手作業の SQL が 1 つでも条件を入れ忘れると、そこから覆されます。
- レビューやテストで漏れを防ぐことはできますが、ゼロにはできません。

### 案 3: キャンセルは楽観的ロックのまま + 状態遷移トリガー → 防げる（入れ忘れたバッチからも）

`tests/Feature/StatusTransitionTriggerTest.php` で、状態遷移のルールを DB トリガーで強制しました。

```sql
CREATE TRIGGER reservations_guard_status_transition BEFORE UPDATE ON reservations
FOR EACH ROW
BEGIN
    IF NEW.status <> OLD.status AND NOT (
           (OLD.status = 'pending'   AND NEW.status IN ('confirmed', 'cancelled'))
        OR (OLD.status = 'confirmed' AND NEW.status = 'cancelled')
    ) THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'invalid reservation status transition';
    END IF;
END
```

| 確認したこと | 結果 |
|---|---|
| 排他制御なしのバッチの後出し | ✅ バッチの UPDATE が DB に拒否され、キャンセルのまま |
| 生の SQL でキャンセル済みを確定にする | ✅ 拒否される |
| 確定を仮予約に戻す（場面 2 の失敗パターン） | ✅ 拒否される |
| 許された遷移、ステータス以外の項目の変更 | 通る |
| 推奨の書き方のバッチ | エラーにならない（そもそも違反する UPDATE を発行しない） |
| 排他制御なしのバッチで、途中の 1 件が違反した場合 | ⚠️ その行でエラーになり、残りの行は処理されずに止まる |

version を上げるトリガー（前述）との違いは、**変更そのものを拒否する** ことです。
version のトリガーは「変更があったことを知らせる」だけで、後出しの UPDATE は成功させてしまいました。
状態遷移のトリガーは、「キャンセル済み → 確定」のように **どの順番で処理されても起きてはいけない変更** を、誰が書いても DB が止めます。

**負荷:** トリガーはロックを取らず、更新する行の新旧の値を比べるだけです。
1 行ずつの UPDATE を 2 万回実行して比べたところ、差は測定のばらつきの範囲内でした（時間の大半はコミットにかかっている）。

| 条件 | 1 件あたり |
|---|---|
| トリガーなし | 約 618〜680 μs |
| トリガーあり | 約 584〜605 μs |

**注意点:**

- 違反した UPDATE はエラーになるので、バッチは途中で止まる。トリガーは「バッチの書き方の誤り」を **データが壊れる前に気づかせる** 仕組みと考え、エラーを監視・通知する。
- トリガーの作成には権限が必要（バイナリログが有効だと SUPER 権限。このテストでも root で作成した）。マイグレーションでの管理方法を、DBA や運用と決める必要がある。
- 業務ルールが DB にも書かれるので、アプリの `ReservationStatus::canTransitionTo()` と二重管理になる。遷移を変えるときは両方を変える。
- 守れるのは「状態の遷移」だけ。ステータス以外の項目の後出しは、案 2 のように書く側の条件で防ぐ。

### どうするべきか（利用者の多いサービスの場合）

**キャンセル処理を悲観的ロックにする必要はありません。** 防げないうえに、利用者を待たせるだけです。

次の 3 層で守るのを推奨します。

| 層 | 内容 | 役割 |
|---|---|---|
| 1. 画面の処理 | キャンセルは楽観的ロック（version または updated_at）+ 状態ガード | 利用者が古い画面のまま操作することを防ぐ |
| 2. バッチ・API | すべての UPDATE に状態ガード（または読んだ時点の version / updated_at）を入れ、version か updated_at を必ず更新する | 後出しを防ぎ、画面の楽観的ロックが変更に気づけるようにする |
| 3. DB | 状態遷移トリガーで、許されない遷移を拒否する | 1・2 のどこかに漏れがあっても、キャンセルが覆らないことを保証する |

どの層もロックを長く持たないので、利用者が増えても待ち時間は増えません。
1・2 で正しく作るのが基本で、3 は「漏れがあったときにデータを壊さず、エラーとして気づかせる」ための保険です。

あわせて、**ステータスの変更は専用の操作（キャンセル、確定など）からだけ行う** ようにします。
このアプリの編集画面のように、フォームでステータスを自由に選べると、古いフォームでステータスが戻る経路が残ります（場面 2）。

## 推奨する設計

### 書き込みのルール

| 処理 | WHERE 句で確認すること | SET すること |
|---|---|---|
| 画面の編集 | `version = 画面を開いた時点` | 変更内容 + `version = version + 1` |
| 画面のキャンセル | `version = 画面を開いた時点` and `status in (キャンセルできる状態)` | `status = 'cancelled'` + `version = version + 1` |
| ステータス変更バッチ | `status = 変更前の状態`（状態ガード） | `status = 変更後` + `version = version + 1` |
| 値を計算して書くバッチ（読んだ値で計算する） | `version = 読んだ時点`（楽観的ロック） | 計算結果 + `version = version + 1` |

**バッチで状態ガードと楽観的ロックを使い分ける基準:**

- **状態ガード:** 書き込む値が「状態」だけで決まる場合（仮予約なら確定にする）。関係ない変更でスキップしない。
- **楽観的ロック:** 読んだ値をもとに計算して書く場合（人数から料金を計算して書くなど）。どの項目が変わっても計算の前提が崩れるので、version で確認する。

### バッチの作り方

- **1 件ずつ（またはチャンクごとに）条件付きで UPDATE し、トランザクションを短くする。**
  全件を 1 つのトランザクションでロックすると、バッチの間は画面の操作が全部待たされる。
- **スキップした予約と理由を記録する。**
  スキップは失敗ではなく「前提が変わっていたので見送った」という正しい動作。次回の実行で改めて判定される。
- **状態遷移のルールに従う。** 許されない遷移のバッチは実行させない。

### version の上げ忘れを防ぐ仕組み

| 方法 | 効果 | 注意点 |
|---|---|---|
| 書き込みを 1 つのクラス（サービス）に集める | アプリの中の経路はこれで揃う | 生の SQL や別システムからの更新は防げない |
| テストで「すべての経路が version を上げる」ことを確認する | 新しい経路を作ったときの漏れに気づける | テストを書き忘れると意味がない |
| version を上げる DB トリガー | 生の SQL を含むすべての更新で version が上がる | 後出しは防げない。権限と運用の調整が必要 |
| **状態遷移の DB トリガー** | 許されない遷移を、誰が書いても拒否する。キャンセルが覆らないことを保証できる | 守れるのは状態の遷移だけ。違反したバッチはエラーで止まる |

## 試し方

```sh
# データを初期状態に戻す
docker compose exec app php artisan migrate:fresh --seed

# ターミナル 1: SQL ログを見る
docker compose exec db tail -f /var/lib/mysql/general.log

# ターミナル 2: 予約 1 を確定するバッチを、読み込み後に 15 秒待つ設定で起動する
docker compose exec app php artisan reservations:change-status pending confirmed --strategy=none --id=1 --pause=15
```

バッチが「15 秒待ちます」と表示している間に、ブラウザで予約 #1 の詳細画面を開き、「この予約をキャンセルする」を押します。
バッチが終わった後に詳細画面を再読み込みすると、`--strategy=none` では確定に戻っています。
`--strategy=state_guard_version` で同じことをすると、キャンセルのまま残り、バッチの出力に「スキップ」と表示されます。
