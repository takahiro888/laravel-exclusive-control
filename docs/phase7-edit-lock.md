# Phase 7: 編集ロック / 有効期限付き編集ロック

## 考え方

これまでの方式は、どれも **保存の瞬間** に競合を確認していました。

- 楽観的ロック（Phase 4・5）: 保存時に「開いた後に変わっていないか」を確認し、変わっていたら後の人が負ける。
- 悲観的ロック（Phase 6）: 保存処理の間だけロックを取り、同時に保存しようとした人を待たせる。

**編集ロック** は、**編集画面を開いた瞬間** にロックを取り、他の人を **そもそも編集画面に入れない** 方式です。
「A さんが編集中です」と表示される、業務システムでよく見る仕組みです。

---

## なぜこの実装が必要なのか

楽観的ロックには「競合に気づくのが保存の瞬間」という弱点がありました（Phase 5）。
B が 10 分かけて入力しても、保存ボタンを押した瞬間に「他の人が先に更新した」と言われ、入力をやり直すことになります。

また悲観的ロック（Phase 6）は、DB のロックが 1 リクエストの中でしか効かないので、画面を開いてから保存するまでを守れませんでした。

編集ロックは、DB のロック機能ではなく、**テーブルの普通のカラムに「誰が編集中か」を書き込む** ことでロックを表現します。

| カラム | 意味 |
|---|---|
| `locked_by` | 誰が編集中か（ロックが無ければ NULL） |
| `locked_at` | いつ編集を開始したか |
| `locked_until` | いつまでロックが有効か（有効期限付きの場合のみ） |

DB に書き込まれた値なので、リクエストや DB 接続をまたいでロックを保持できます。
このようなロックを **アプリケーションレベルのロック**（論理ロック）と呼びます。

---

## 操作者の識別

ロックには「誰が」持っているかが必要です。このアプリはログイン機能を持たないので、ヘッダーの **操作者** 欄で名前を設定します。

- 操作者名はブラウザのセッションに保存されます。初回は「利用者-1234」のような仮の名前が付きます。
- セッションは Cookie 単位なので、**同じブラウザの別タブは同じ操作者** になります。
- A と B を検証するときは、**別のブラウザ** か **通常ウィンドウとプライベートウィンドウ** を使い、それぞれ「A」「B」のような名前にします。

---

## 排他制御のタイミング

| タイミング | 編集ロック | 有効期限付き編集ロック |
|---|---|---|
| **編集画面を開く** | **ロックを取る**。他の人が持っていれば追い返す | **ロックを取る**。他の人が持っていても、**期限切れなら奪える** |
| 編集中 | ロックを保持し続ける | 期限までロックを保持する。再読み込みすると期限が延長される |
| 保存 | 自分がロックを持っているか確認して更新し、同じ UPDATE でロックを外す | 同左 |
| キャンセル | 「キャンセル（ロック解放）」ボタンでロックを外す | 同左 |
| 画面を閉じて放置 | **ロックが永久に残る**（強制解除が必要） | 期限が来れば他の人が奪える |

---

## 発行される SQL

### ロックの取得（編集画面を開いたとき）

```sql
-- 有効期限なし
update `reservations`
   set `locked_by` = 'A', `locked_at` = NOW(), `locked_until` = NULL
 where `reservations`.`id` = 1
   and (`locked_by` is null or `locked_by` = 'A')

-- 有効期限あり（60 秒）
update `reservations`
   set `locked_by` = 'A', `locked_at` = NOW(), `locked_until` = NOW() + INTERVAL 60 SECOND
 where `reservations`.`id` = 1
   and (`locked_by` is null or `locked_by` = 'A' or `locked_until` < NOW())   -- 期限切れなら奪える
```

- 「誰もロックしていない」か「自分がロックしている」場合だけ一致し、1 件更新になります。
- 他の人がロック中なら一致する行が無く 0 件になり、「A さんが編集中」と表示して詳細画面に戻します。

### 保存

```sql
update `reservations`
   set `customer_name` = '山田 太郎', `number_of_people` = '4', ...,
       `locked_by` = NULL, `locked_at` = NULL, `locked_until` = NULL,
       `reservations`.`updated_at` = '2026-10-04 15:56:29'
 where `reservations`.`id` = 1
   and `locked_by` = 'A'       -- 自分がまだロックを持っている場合だけ
```

### キャンセルと強制解除

```sql
-- キャンセル: 自分のロックだけを外す
update `reservations` set `locked_by` = NULL, `locked_at` = NULL, `locked_until` = NULL
 where `reservations`.`id` = 1 and `locked_by` = 'B'

-- 強制解除: 誰のロックでも外す
update `reservations` set `locked_by` = NULL, `locked_at` = NULL, `locked_until` = NULL
 where `reservations`.`id` = 1
```

## 実験

### 実験 1: 基本の流れ（有効期限なし）

| 操作 | 結果 | DB（locked_by / updated_at） |
|---|---|---|
| 初期状態 | | NULL / 15:56:28 |
| A が編集画面を開く | 入れた | **A** / 15:56:28 |
| B が編集画面を開く | **追い返された**「A さんが編集中のため、編集できません（15:56:29 から編集中）」 | A / 15:56:28 |
| A が人数を 4 にして保存 | 成功 | **NULL** / 15:56:29 |
| B が編集画面を開く | 入れた | **B** / 15:56:29 |
| B がキャンセル | ロック解放 | **NULL** / 15:56:29 |

ロックの取得とキャンセルでは `updated_at` が変わっていないことに注目してください（後述）。

### 実験 2: ロックを放置した場合（有効期限なし vs あり）

A が編集画面を開いたまま、キャンセルせずにブラウザを閉じた場合です。

**有効期限なし:**

```
15:56:43  A が編集画面を開く → ロック取得
          A はキャンセルせずにブラウザを閉じた
15:57:48  65 秒後に B が編集画面を開く → 追い返された「A さんが編集中のため、編集できません」
15:57:48  B が詳細画面で「強制解除」 → locked_by = NULL
15:57:48  B が編集画面を開く → 入れた
```

ロックは何秒たっても外れません。強制解除しない限り、誰もこの予約を編集できなくなります。

**有効期限あり（60 秒）:**

```
15:57:49  A が編集画面を開く → locked_by = A, locked_until = 15:58:49
15:57:50  B が編集画面を開く → 追い返された
15:58:52  62 秒後に B が編集画面を開く → 入れた（期限切れのロックを奪った）
          locked_by = B, locked_until = 15:59:52
15:58:52  A（期限切れ）が人数を 4 にして保存 → 失敗
          「編集ロックが失われました。現在は B さんが編集中です」
15:58:52  B がステータスを確定にして保存 → 成功
```

A の保存の WHERE 句は `locked_by = 'A'` ですが、B がロックを奪った時点で `locked_by = 'B'` になっているので 0 件更新になります。
期限切れの A が古い内容で上書きすることはありません。

### 実験 3: 期限切れでも、誰も奪っていなければ保存できる

```
15:59:43  A が編集画面を開く（locked_until = 16:00:43）
16:00:45  期限切れ（locked_by = A のまま）
16:00:46  A が保存 → 成功
```

保存時は期限を確認せず、`locked_by = 自分` だけを確認しています。
期限が切れていても、誰もロックを取っていなければ、その間に他の人は編集していません。保存を許しても Lost Update は起きません。

### 実験 4: 再読み込みで期限が延長される

```
1 回目:  locked_at = 16:00:47, locked_until = 16:01:47
3 秒後:  locked_at = 16:00:50, locked_until = 16:01:50   ← 自分のロックを取り直し、期限が延びた
```

### 実験 5: 10 人が同時に編集画面を開く

| 編集画面に入れた | 追い返された | 発行された UPDATE 文 |
|---|---|---|
| **1 人** | 9 人 | 10 件 |

10 件のロック取得の UPDATE がほぼ同時に届いても、ロックを取れたのは 1 人だけでした。
Phase 5 と同じく、InnoDB が UPDATE の対象行に行ロックを取ってから WHERE 句を評価するためです。

## 実装のポイント

### 1. ロックは条件付きの UPDATE 1 文で取る

次のような書き方は **間違い** です。

```php
if ($reservation->locked_by === null) {      // ① 空いているか確認
    $reservation->locked_by = $operator;     // ② ロックを取る
    $reservation->save();
}
```

①と②の間に他の人が割り込むと、2 人ともロックを取れてしまいます（Check-Then-Act の競合）。
条件付きの UPDATE 1 文にすれば、確認と書き込みの間に割り込む隙間がありません。実験 5 がその確認です。

これは楽観的ロックの「UPDATE の WHERE 句で確認する」と同じ考え方です。
編集ロックは、**ロックの取得そのものに楽観的ロックと同じ仕組みを使っている** と言えます。

### 2. ロック操作では updated_at を変えない

Eloquent の `Builder::update()` は、`updated_at` を自動で SET に加えます。
ロック操作は業務データの変更ではないので、`toBase()` で素のクエリビルダーに切り替え、`updated_at` を変えないようにしています。

```php
Reservation::query()->whereKey($id)->where(...)
    ->toBase()     // ← これが無いと updated_at = 現在時刻 も SET される
    ->update(['locked_by' => $operator, ...]);
```

もし `updated_at` が変わると、次のような問題が起きます。

- 一覧の「最終更新日時」が、編集画面を開いただけで変わってしまう。
- updated_at 方式の楽観的ロックと併用している場合、編集画面を開いただけで他の人の保存が競合になる。

### 3. 期限は MySQL の NOW() で計算・比較する

```sql
`locked_until` = NOW() + INTERVAL 60 SECOND
`locked_until` < NOW()
```

PHP の `now()` で計算すると、Web サーバーが複数台ある場合にサーバーごとの時計のずれで判定が変わります。
期限の計算と比較を DB の時計 1 つに揃えています。

### 4. 操作者はセッションから取る

保存処理に渡す操作者名は、フォームの入力ではなく **サーバー側のセッション** から取っています。
フォームから受け取ると、他人の名前を送ってロックをすり抜けることができてしまいます。

### 5. キャンセルはリンクではなくフォームで送る

「キャンセル」がただのリンクだと、ロックが残ったままになります。
ロックを外すには DB の更新が必要なので、DELETE リクエストを送るボタンにしています。

### 6. ロックを失った保存は詳細画面に戻す

楽観的ロックでは、競合したら入力内容を残して編集画面に戻していました。
編集ロックで同じことをすると、編集画面がロックの取得を試み、B が持っていればさらに詳細画面へ転送されます。
その結果、「ロックが失われた」というメッセージが「B さんが編集中」で上書きされてしまいました（実装中に発見して修正）。
そのため、編集ロック方式でロックを失った場合は、詳細画面に直接戻しています。

## 弱点と注意点

### 弱点 1: 放置されたロック（有効期限なし）

実験 2 のとおり、キャンセルせずにブラウザを閉じる、別のページに移動する、PC がスリープするなどでロックが永久に残ります。
強制解除の機能が必須になり、「誰が解除してよいか」という運用ルールも必要です。

### 弱点 2: 有効期限の長さのトレードオフ（有効期限あり）

| 期限 | 問題 |
|---|---|
| 短すぎる | 入力中にロックが切れ、他の人に奪われる。保存しようとすると「ロックが失われました」になる |
| 長すぎる | 放置されたロックが外れるまで、他の人が長く待たされる |

実務では、編集画面から JavaScript で定期的にサーバーへ通知して期限を延長する（ハートビート）ことがあります。
このアプリでは、編集画面の再読み込みで延長するだけにしています。

### 弱点 3: 同じ操作者の複数タブは守れない

`locked_by = 自分` ならロックを取り直せるので、同じ人が 2 つのタブで編集画面を開くと両方に入れます。
その 2 つのタブの間では Lost Update が起きます。
対策として、ロックごとにランダムなトークンを発行して hidden で送り、操作者名ではなくトークンで照合する方法があります。

### 弱点 4: 操作者名の重複

このアプリは操作者名でロックの持ち主を判定しているので、2 人が同じ名前にすると同じ人として扱われます。
実務では、ログインユーザーの ID で判定します。

### 弱点 5: ロックを無視する更新経路

編集ロックは、アプリが「locked_by を確認する」というルールを守っている場合だけ効きます。
DB が強制するロックではないので、次のような更新はロックを無視します。

- このアプリの削除ボタン（ロック中でも削除できる）
- 他の方式で保存した場合
- バッチ処理や手作業の SQL

### 弱点 6: GET リクエストで DB を更新している

このアプリは、他の方式と同じ操作で比較できるよう、編集画面を開く GET リクエストでロックを取っています。
GET はブラウザの先読みやクローラーで意図せず実行されることがあるので、本来は副作用を持たせるべきではありません。
実務では、詳細画面に「編集を開始する」ボタンを置き、POST でロックを取ることが多いです。

## 6 方式の比較

| | なし | updated_at | version | FOR UPDATE | 編集ロック | 期限付き編集ロック |
|---|---|---|---|---|---|---|
| ロックを取るタイミング | - | -（保存時に確認） | -（保存時に確認） | 保存処理の間 | 編集画面を開いたとき | 編集画面を開いたとき |
| ロックの実体 | - | - | - | DB の行ロック | テーブルのカラム | テーブルのカラム |
| 競合に気づくタイミング | 気づけない | 保存時 | 保存時 | 保存時（待たされた後） | **編集画面を開くとき** | **編集画面を開くとき** |
| 後から来た人 | 上書きする | 保存時にエラー | 保存時にエラー | 待たされる | 編集画面に入れない | 編集画面に入れない（期限切れなら入れる） |

| 追加のカラム | - | 不要 | version | 不要 | locked_by, locked_at | locked_by, locked_at, locked_until |
