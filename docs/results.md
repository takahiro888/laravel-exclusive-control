# 検証結果のまとめ

Phase 3〜8 で行った検証の結果を、方式どうしで比べられるようにまとめた資料です。
各結果の詳しい手順と、実際の SQL ログは、各 Phase のドキュメントにあります。

---

## 1. 結論

| 方式 | Lost Update を防げるか | 一言での評価 |
|---|---|---|
| 排他制御なし | **防げない** | 比較の基準。後から保存した人が気づかないまま上書きする |
| 楽観的ロック（updated_at） | ほぼ防げる | カラム追加なしで導入できる。ただし同じ秒の更新を見逃す |
| 楽観的ロック（version） | **防げる** | 画面をまたぐ編集の標準的な選択肢。競合に気づくのは保存時 |
| 悲観的ロック（SELECT FOR UPDATE） | **単独では防げない** | 1 リクエスト内の「読んで、計算して、書く」処理向き。画面をまたぐ編集には version 確認との併用が必要 |
| 編集ロック | 防げる | 他の人を編集画面に入れない。放置されたロックが永久に残る |
| 有効期限付き編集ロック | 防げる | 放置の問題を期限で解決。期限の長さの調整が必要 |

ただし、これは「同じ画面どうし」の結論です。
**画面とバッチのように別の処理が混ざると、どの方式でも、すべての書き込み経路が同じルールに従わない限り防げません。**
その検証と最善の書き方は「[8. 異なる処理の組み合わせ](#8-異なる処理の組み合わせ画面--バッチ)」にまとめています。

## 2. 共通の検証手順と結果

予約 #1（2名 / 仮予約）を A と B が同時に開き、A が人数を 4名 に、B がステータスを確定に変えて、A → B の順に保存しました。

| 方式 | B の保存 | 最終的な人数 | 最終的なステータス | 詳細 |
|---|---|---|---|---|
| 排他制御なし | 成功 | **2**（A の変更が消えた） | 確定 | [phase3](phase3-lost-update.md) |
| updated_at | 競合で止まる | 4 | 仮予約 | [phase4](phase4-updated-at.md) |
| version | 競合で止まる | 4 | 仮予約 | [phase5](phase5-version.md) |
| SELECT FOR UPDATE（version 確認あり） | 競合で止まる | 4 | 仮予約 | [phase6](phase6-pessimistic-lock.md) |
| SELECT FOR UPDATE（version 確認なし） | 成功 | **2**（A の変更が消えた） | 確定 | [phase6](phase6-pessimistic-lock.md) |
| 編集ロック | B は編集画面に入れない | 4 | 仮予約 | [phase7](phase7-edit-lock.md) |

楽観的ロックで競合した B は、「最新の内容」と「自分の入力」を見比べてから保存し直せます。保存し直すと 4名 / 確定 になりました。

## 3. 方式ごとの比較

### 排他制御のタイミングと SQL

| 方式 | いつ確認・ロックするか | 保存時の SQL（要点） |
|---|---|---|
| 排他制御なし | しない | `update ... where id = ?` |
| updated_at | 保存時の UPDATE 1 回 | `update ... where id = ? and updated_at = ?` |
| version | 保存時の UPDATE 1 回 | `update ..., version = version + 1 where id = ? and version = ?` |
| SELECT FOR UPDATE | 保存トランザクションの間 | `select ... for update` → PHP で version を確認 → `update ... where id = ?` → `commit` |
| 編集ロック | 編集画面を開いたとき | 開くとき `update ... set locked_by = ? where id = ? and (locked_by is null or locked_by = ?)`、保存時 `update ... where id = ? and locked_by = ?` |
| 有効期限付き編集ロック | 編集画面を開いたとき | 開くときの条件に `or locked_until < NOW()` が加わる |

### 競合したときの体験

| 方式 | 後から来た人に起きること | 気づくタイミング |
|---|---|---|
| 排他制御なし | 何も起きない（上書きする） | 気づけない |
| updated_at / version | 保存時にエラー。入力は残り、最新の内容と並べて表示される | 保存ボタンを押したとき |
| SELECT FOR UPDATE | 先の人の保存が終わるまで **待たされる**。その後エラー | 保存ボタンを押したとき（待たされた後） |
| 編集ロック | 編集画面に入れず「A さんが編集中」と表示される | 編集画面を開こうとしたとき |

### 実装と運用

| | なし | updated_at | version | FOR UPDATE | 編集ロック | 期限付き |
|---|---|---|---|---|---|---|
| 追加のカラム | - | 不要 | version | 不要 | locked_by, locked_at | + locked_until |
| ロックの実体 | - | - | - | DB の行ロック | テーブルのカラム | テーブルのカラム |
| 放置されたときのリスク | - | なし | なし | なし（トランザクション終了で解放） | **永久に残る** | 期限まで残る |
| 利用者が待たされるか | いいえ | いいえ | いいえ | **はい**（最大 innodb_lock_wait_timeout） | いいえ | いいえ |
| 他の更新経路への要求 | - | updated_at を更新すること（Eloquent なら自動） | **version を +1 すること** | 同じ行をロックすること | locked_by を確認すること | 同左 |

## 4. 方式ごとの実験結果

### updated_at と version: 同じ秒の中の更新（Phase 4・5）

1 秒以内に「A が保存 → B が開く → A がもう一度保存」を行い、その後 B が保存しました。

| 方式 | B が受け取った hidden | A の 2 回目の保存後 | B の保存 | 最終的な人数 |
|---|---|---|---|---|
| updated_at | 18:08:09 | 18:08:09（**変わらない**） | 成功してしまう | 4（A の 6 が消えた） |
| version | 2 | 3 | 競合で止まる | 6（守られた） |

### version: 10 件の保存を同時に送る（Phase 5）

| 方式 | 成功 | 競合 |
|---|---|---|
| 排他制御なし | 10 件（9 件分の変更が消えた） | 0 件 |
| version | **1 件** | 9 件 |

10 件の UPDATE はほぼ同じミリ秒に届きましたが、成功は 1 件だけでした。
InnoDB が UPDATE の対象行に行ロックを取ってから WHERE 句を評価するためです。

### SELECT FOR UPDATE: ロック待ちとタイムアウト（Phase 6）

| 実験 | 結果 |
|---|---|
| A がロックを 5 秒持つ間に B が保存 | B は約 4 秒待たされ、A のコミット後に最新の version を読んで競合になった |
| A がロックを 15 秒持つ間に B が保存 | B は 10 秒（innodb_lock_wait_timeout）でタイムアウトし、メッセージを表示した |
| ロック中に詳細画面（通常の SELECT）を開く | 0.09 秒で表示された。コミット前の変更は見えない |
| version 確認なしで同時に保存 | B は 4 秒待たされた後、A の変更を上書きした |

### 編集ロック: 放置と有効期限（Phase 7）

| 実験 | 有効期限なし | 有効期限あり（60 秒） |
|---|---|---|
| A が開いたまま放置し、60 秒あまり後に B が開く | 入れない（強制解除が必要） | 入れる（期限切れのロックを奪う） |
| ロックを奪われた A が保存する | - | 拒否される |
| 期限切れだが誰も奪っていない状態で A が保存する | - | 成功する |
| 10 人が同時に編集画面を開く | - | 1 人だけ入れた |

## 5. 方式の選び方

```
画面を開いてから保存するまでの間の変更を守りたい？
├─ いいえ（1 リクエストの中で「読んで、計算して、書く」処理）
│    例: 在庫を 1 減らす、残席を確認して予約する
│    → SELECT FOR UPDATE
│
└─ はい（画面をまたぐ編集）
     │
     競合はよく起きる？ 入力に時間がかかる画面？
     ├─ いいえ → 楽観的ロック
     │            ├─ 新規開発、またはカラムを追加できる → version
     │            └─ 既存テーブルにカラムを追加できない → updated_at（同じ秒の見逃しを許容できる場合）
     │
     └─ はい → 編集ロック
                  └─ 放置されたロックを自動で解放したい → 有効期限付き（実務ではほぼこちら）
```

組み合わせることもよくあります。

- **編集ロック + version**: 編集ロックを無視する更新経路（API やバッチ）があっても、version で最後の砦を作る。
- **SELECT FOR UPDATE + version**: Phase 6 で実装した形。画面をまたぐ変更は version で検知し、同時の保存はロックで順番に並べる。

## 6. 検証で分かったこと

### 確認は「1 つの SQL 文」で行う

「確認してから更新する」を 2 つの処理に分けると、その間に他の更新が割り込めます（Check-Then-Act の競合）。

- 楽観的ロックは、確認を UPDATE の WHERE 句に入れて 1 文にする。
- 編集ロックの取得も、条件付きの UPDATE 1 文で行う（10 人同時でも 1 人だけが取れた）。
- 例外は SELECT FOR UPDATE。ロックを持っている間は割り込まれないので、PHP の if で確認してよい。

### DB のロックは 1 リクエストの中でしか効かない

PHP-FPM はリクエストごとに新しい DB 接続を作ります。general log の接続 ID も、リクエストごとに変わっていました。
「画面を開いてから保存するまで」は複数のリクエストにまたがるので、DB のトランザクションやロックでは守れません。
編集開始時の値を hidden で持ち回るか（楽観的ロック）、DB のカラムにロックを書き込む（編集ロック）必要があります。

### MySQL の UPDATE の件数は「値が変わった行数」

デフォルトでは、WHERE 句に一致しても値が変わらなければ 0 件と数えられます。
楽観的ロックは「0 件なら競合」と判定するので、変更なしで保存すると誤って競合になりました。
`Pdo\Mysql::ATTR_FOUND_ROWS => true` で「一致した行数」を返すようにして解決しました（[phase4](phase4-updated-at.md)）。

### Eloquent の便利さが排他制御の邪魔をすることがある

| 挙動 | 影響 | 対処 |
|---|---|---|
| `save()` は変わったカラムだけを UPDATE する | 一見 Lost Update を防げそうだが、フォームが古い値を送るので防げない | 楽観的ロック等で確認する |
| `Builder::update()` は casts を通らない | 日時がフォームの形式のまま SQL に入る | 一度モデルに fill して変換する |
| `Builder::update()` は updated_at を自動で更新する | 編集ロックの取得だけで updated_at が変わってしまう | ロック操作は `toBase()` で素のクエリビルダーを使う |
| 競合時に `old()` で hidden を復元する | 古い値が戻り、何度保存しても競合する | hidden は必ず DB の最新値を出す |

### 時刻を扱うなら、時計を 1 つに揃える

PHP・MySQL・Laravel のタイムゾーンを Asia/Tokyo に揃えました。
さらに編集ロックの期限は、PHP の `now()` ではなく MySQL の `NOW()` で計算・比較しています。
Web サーバーが複数台になっても、サーバーごとの時計のずれで判定が変わらないようにするためです。

### 排他制御は「全員が同じルールに従う」ことで効く

- version 方式は、すべての更新経路が version を +1 しないと検知できない。
- 編集ロックは DB が強制するロックではないので、削除ボタンやバッチ処理はロックを無視できる（テストで確認済み）。
- このアプリでも、方式の設定はブラウザごとではなくアプリ全体で 1 つにしている。

## 8. 異なる処理の組み合わせ（画面 × バッチ）

楽観的ロックのキャンセル処理と、書き方の違うステータス変更バッチを、同じ予約に対して動かしました（[phase10](phase10-combinations.md)）。

| バッチの書き方 | バッチの後出し | 利用者の後出し | 知らずにキャンセル | バッチ同士 | 関係ない編集 |
|---|---|---|---|---|---|
| なし | ❌ キャンセルが確定で上書き | ❌ 確定が仮予約に戻る | ⚠️ 気づけない | ❌ 上書き | ✅ |
| 状態ガード | ✅ | ❌ 確定が仮予約に戻る | ⚠️ 気づけない | ✅ | ✅ |
| **状態ガード + version** | ✅ | ✅ | ✅ | ✅ | ✅ |
| 楽観的ロック | ✅ | ✅ | ✅ | ✅ | ⚠️ 不要なスキップ |
| 悲観的ロック | ✅ | ✅ | ✅ | ✅ | ✅（ただしロックの負荷） |

**最善:** すべての書き込み経路が、次の 2 つを守ること。

1. 書き込むときに「読んだ時点の前提」を UPDATE の WHERE 句で確認する（後出しを防ぐ）。
2. 業務データを変えたら必ず version を上げる（他の処理の楽観的ロックが気づけるようにする）。

ステータス変更バッチでは「状態ガード + version」が最善でした。
DB トリガーで version の上げ忘れは防げますが、後出しは防げません。
また、version を確認しない編集ロック方式の画面は、推奨の書き方のバッチと組み合わせても、バッチの変更を古いフォームで戻してしまいました。
